# Драйвер CT-серии: калибровка 4/4H, затем CT-14

База: `main` @ `058374ab`. Две фазы одной работы. **Фаза A** — доделать механизм калибровок Anytime 4/4H (CT3), который в репозитории в полуготовом виде. **Фаза B** — добавить CT-14 (CT2) поверх уже исправного калибровочного слоя.

Именование: сенсор называем по имени трансмиттера — **CT-14** и **4 / 4H**, без вендорских префиксов.

Источник истины по алгоритму и калибровке — **Blueberry** (`apex-re-bb430`). Его реализация мультиплатформенная и улучшена относительно вендорской: вендорский `libalgorithm-jni.so` — только arm64/armv7 и в сборку не пакуется. `~/Downloads/MK4_FINAL_SUMMARY.md` — реверс вендорского native, он описывает *базовую цепочку*, но не является целью: Blueberry поверх неё добавляет слой пользовательской калибровки, которого в вендоре нет.

### A1 · Пользовательская калибровка — affine-слой

**Это главный пункт всей фазы.** Сейчас `computeCalibrated(record, k0, contiguous, rawLinear)` не принимает `lastReferenceBgMgdlTimes10` / `lastReferenceBgGlucoseId`. Они приходят в `compute()` из `AnytimeBleManager.kt:2848`, но используются только на native-путях, а native `.so` не пакуется — значит на единственном работающем пути укол пальцем не влияет ни на что.

Реализовать по модели Blueberry:

1. Хранилище точек под ключом `calibrations`: `(timestampMs, glucoseId, referenceMgdl, ib, iw, sensorTemp, filteredAtEntry)`.
2. Расчёт `slope` / `intercept` по накопленным точкам. Одна точка — только `intercept` (сдвиг) либо `slope` через начало координат; решение зафиксировать явно и обосновать, а не оставить на усмотрение кода. Две и более — взвешенная регрессия с затуханием веса по возрасту точки.
3. Применение поверх выхода модели: `glucose = slope · filtered + intercept`.
4. Сохранение `slope` и `intercept` **в каждой записи** — как в Blueberry. Это даёт пересчёт истории при добавлении или удалении точки без повторного прохода по сырым токам.
5. Пересчёт по `onUserCalibrationRevisionChanged` — метод уже есть в контракте `ManagedBluetoothSensorDriver`.
6. Заводские `K` / `R` хранить отдельно (`anytimeFactoryK` / `anytimeFactoryR`), не смешивая с пользовательскими точками.

**Приёмка.** Укол пальцем меняет отображаемое значение без наличия native `.so`. Удаление точки возвращает предыдущие `slope` / `intercept`. Тест: две точки → ожидаемая прямая; ноль точек → выход модели без изменений.

### A3 · Персист состояния калибратора

`computeCalibrated` создаёт новый `AnytimeCalibrator` на каждую запись и переигрывает весь префикс 0…id. Это противоречит контракту самого класса («Hold one instance per sensor session, not per record») и даёт на бэкфилле полной истории порядка 23 млн шагов плюс столько же аллокаций — комментарий у `rawRecordsForAlgorithm` (`AnytimeBleManager.kt:1162`) прямо предупреждает «without O(n²) copies», и это ровно то, что вернули.

Blueberry решает иначе: сохраняет состояние калибратора и восстанавливает его из последней записи (`Native calibrator state restored from last record #`). Сохранять надо `tempSmoothPrev`, `filteredPrev`, `lastGlucoseId`.

**Приёмка.** Один экземпляр на сессию. Перезапуск приложения даёт тот же ряд, что и непрерывная сессия (тест на идентичность). Бэкфилл 6740 записей — один проход.

---

### A4 · Молчаливое переключение между моделями

Гейт нового пути — `contiguous.isNotEmpty()`, а `contiguousHistoryThrough` возвращает пустой список, если в диапазоне 0…id пропущена **хотя бы одна** запись. Один пробел от разрыва связи — и все последующие чтения тихо уходят в `computeLinear` (`K·Iw + R/100`), то есть в ту самую формулу, которую комментарий нового кода называет причиной систематического сдвига. Пользователь видит ступеньку на графике без единого признака.

После A3 проблема снимается по существу: восстановление состояния убирает требование непрерывного префикса. Остаётся явно решить, что делать при реальном пробеле — и в любом случае показать смену модели в интерфейсе, а не менять её молча.

**Приёмка.** Смена расчётного пути отражается в `sensorDetailTelemetry` и логируется. Тест: пробел в истории не приводит к скачку значения без индикации.

### A6 · Тесты

Текущие 4 теста проходят (пересчитал вручную), но покрытие узкое: на окне log7 все дельты около `0.05` против `r ≈ 1.34`, поэтому **обе ветки отсечения ограничителя шага, ветка `x > 60` и ветка `≥ 50` не исполняются ни разу** — то есть самая хрупкая часть §7 не покрыта. Тест `resetReSeedsFilter` тавтологичен: обе половины возвращают одно и то же потому, что лимитер не срабатывает.

Добавить:

* синтетический ряд с резким подъёмом (`delta > r`) — проверка формулы `min((x + prev·delta)/(delta + 1), prev + r)`;
* резкий спад (`delta < −r`) — `prev − r`;
* `x > 60` и `cand ≥ 50 && x ≥ 50`;
* ветка холодной температуры `T ≤ 30` — после решения по A5.1;
* пользовательская калибровка: ноль / одна / две точки, удаление точки;
* каждый гейт из A2;
* сохранение и восстановление состояния (A3);
* регрессия: ряд из log18 (`GlucoseID 1428…1451`) — документ даёт по нему MAE ≈ 0.040.

**Отдельный критерий:** тесты сверяются с колонкой `Glu_AI_replay`, а не `Glu_AI факт`. Расхождение между ними в документе есть и растёт с уровнем — пакет 430: 5.063 против 5.092; пакет 1435: 10.504 против 10.697, то есть с 0.6 % до 1.8 %. Это остаток относительно **вендорского** native. Поскольку целью выбран Blueberry, а не вендор, остаток допустим — но он должен быть зафиксирован в документации как известное и намеренное расхождение, а не замаскирован формулировкой «replaces the approximation which caused the systematic offset» в комментарии `AnytimeAlgorithm.kt:424`.

## 3. Фаза B — CT-14

Начинается после закрытия A1–A6. К этому моменту калибровочный слой общий и исправный, поэтому для CT-14 остаётся протокол и профиль.

### Главный вывод по CT-14

**CT-14 — это CT2-профиль того же вендорского SDK `ist.com.sdk`, чей CT3-профиль уже реализован как драйвер `anytime`.**

| Что уже есть в дереве | Где |
|---|---|
| Шапка: «Reverse-engineered from com.anytime.rus / com.kamin.cgmblelib + **ist.com.sdk**» | `AnytimeConstants.kt:1` |
| `Family.CT2("CT2", needsLegacyUuids = true)` в enum семейств | `AnytimeConstants.kt` ≈291 |
| Все CT2-префиксы в `FAMILY_TABLE`: SN04, SN06, SN08, SN12, SN18, SN20, SN22, SN48, SN50, SN52 | `AnytimeConstants.kt` ≈322 |
| UUID `FFF0` / write `FFF1` / notify `FFF2` объявлены и работают как fallback при discovery | `AnytimeBleManager.kt:2077` |
| Kotlin-заглушки вендорского SDK с CT2-записями в `EDevice` | `java/ist/com/sdk/` |

Откуда «14»: у всех CT2 интервал 3 мин, `endNumber = 6740` даёт 337 ч ≈ **14.04 суток**. Кандидаты — `SN20 / SN48 / SN50 / SN52` (алгоритм 7), `SN04` (алг. 8), `SN08` (`endNumber 6720`, алг. 1). Семидневки — `SN18` (3380). Точный префикс фиксируется по реальному имени устройства.

**Архитектура:** CT2-вариант внутри `drivers/anytime/`, наружу — отдельный тип сенсора «CT-14». Отдельный пакет с нуля означал бы форк `AnytimeBleManager.kt` (4204 строки готового автомата: discovery, переподключение, бэкфилл, таймауты, дедуп) — второй экземпляр этого кода стал бы вторым экземпляром его багов. Раздельным остаётся только то, что видит пользователь: своя запись в `SensorType`, свой мастер, своя `ManagedSensorUiFamily`, свои строки.

### B0 · Разведка *(блокирующая)*

Снять реальное имя устройства CT-14 при сканировании и сопоставить с `FAMILY_TABLE` — это определяет ресурс, прогрев и id алгоритма. Снять btsnoop полной сессии официального приложения: подключение → handshake → init → set time → первые push-записи → одна калибровка.

**Приёмка.** Известен префикс `SNxx`, подтверждены UUID, есть минимум один сырой кадр глюкозы и один кадр check в hex. Кадр калибровки — отдельно, см. ниже.

**В процессе (2026-09-07).** Живой захват через Magisk-root, `persist.bluetooth.btsnooplogmode = full`, рабочий сенсор `SN08402458`, MAC `94:A9:A8:47:89:0E`, подключён в Blueberry. Префикс — **`SN08`**, что закрывает открытый вопрос №5: `Family.CT2, algorithm 1, endNumber 6720` → прогрев `20×3 = 60 мин`, ресурс `6720×3 = 20160 мин = ровно 336 ч = 14.0 суток`. Точнее совпадение с названием «CT-14», чем предполагавшиеся ранее `SN20/48/50/52` (337 ч).

Service discovery подтвердил топологию из `AnytimeConstants.SERVICE_LEGACY_CT2`: сервис `FFF0` на handle `0x0023`, характеристика записи `FFF1` на `0x0025`, характеристика уведомлений `FFF2` на `0x0028` (Wireshark подписывает их как «Public Key Open Credential» / «Aliro» / «ICCE Digital Key» — совпадение по номеру UUID с новым SIG-сервисом цифровых ключей, не имеет отношения к сенсору).

За первые ~5 минут сессии (handshake → setDate → check, ещё до конца прогрева) захвачены и побайтово сверены с §B1 три кадра — см. ниже.

### B1 · Кадры CT2

Источник — `ist/com/sdk/ProtocolToolsHolder.java` из `POCTech_xDrip_v_0.2.apk` (672 стр. читаемой Java, без обфускации).

Кадры без заголовка и преамбулы, последний байт — сумма всех предыдущих по модулю 256. CRC нет.

| Назначение | TX | Ответ |
|---|---|---|
| Версия трансмиттера | `03` | 7 байт; ver = b1·1000 + b2·100 + b3·10 + b4, месяц b5, день b6 |
| Handshake | `48 <ASCII имя…> sum` | `48 55 AA sum` — фиксированный 4-байтный ACK, подтверждено вживую |
| Установка времени | `54 yrHi yrLo mon day hh mm ss sum` | `54 55 AA sum` — фиксированный 4-байтный ACK, подтверждено вживую |
| Init | `53 55 AA 52` | проверка суммы |
| Self-test / check | `43 55 AA 42` | 8 байт: `Iw` int16 BE /10 (b1–2), `Ib` int16 BE /10 (b3–4), температура (b5, бит 7 → +0.5), ток/батарея (b6), сумма (b7). `temp ≥ 50` → отказ по температуре, `b6 < 50` → отказ по питанию. Раскладка `Iw`/`Ib`/`T` не из SDK — расшифрована вживую (см. ниже); вендорский `checkResponse()` эти байты игнорирует и смотрит только на b5/b6 |
| Low power | `57 55 AA 56` | проверка суммы |
| Unbind | `58 55 AA 57` | проверка суммы |
| Запрос записи по id | `55 idHi idLo sum` | 15 байт, opcode `0x47` (не совпадает с opcode живого push `0x44` — подтверждено вживую, см. ниже) |
| Калибровка, референс мг/дл | `08 mgdlHi mgdlLo sum` | `[0] = 08` и корректная сумма |
| Глюкоза от трансмиттера | `09 idHi idLo` | `[0] = 09` → `GluMG` / `GluMM` |

Опкоды CT2 — ASCII-буквы: `'C'` check, `'S'` init, `'T'` time, `'U'` pull, `'W'` low-power, `'X'` unbind, `'H'` handshake. У CT3 и CT2.5 формы другие; значения `0x08` и `0x09` есть в обоих семействах, но означают разное.

**Живой захват, `SN08402458`, 2026-09-07 20:07–20:14 MSK** (см. B0):

```
TX handshake  48 53 4e 30 38 34 30 32 34 35 38 88   sum OK, ASCII "SN08402458"
RX ack        48 55 aa 47                            sum OK

TX setDate    54 07 ea 09 07 14 07 18 88             sum OK
                 ├── year  = 0x07ea = 2026
                 ├── month = 0x09   = 9
                 ├── day   = 0x07   = 7
                 └── time  = 20:07:24  (реальное время на телефоне в момент кадра)
RX ack        54 55 aa 53                             sum OK

TX check      43 55 aa 42                             sum OK
RX            43 00 82 00 17 1c 64 5c                 sum OK
                 ├── b5 (temp byte) = 0x1c = 28  → < 50, проверка проходит
                 └── b6 (power byte) = 0x64 = 100 → ≥ 50, проверка проходит
```

Аргумент handshake — это **собственное рекламируемое имя устройства** (`"SN08402458"`), не серийник в другом формате и не id пользователя — закрывает открытый вопрос №6. Ответы handshake/setDate — не произвольный мусор с верной суммой, а конкретные фиксированные ACK-кадры `{opcode, 0x55, 0xAA, sum}`; это стоит закладывать в парсер как точное сравнение, а не только `isLegal()`.

Check-кадр оказался 8 байт, а не 7 — SDK читает только `b[5]`/`b[6]` и байты 1–4 отбрасывает. Byte-поля 1–4 расшифрованы отдельно, через процедуру «самопроверки с током и температурой» в Blueberry (доступна во время прогрева — тот же `0x43`, просто Blueberry разбирает больше байт, чем вендорский `checkResponse()`):

```
Эталон с экрана Blueberry:           Iw = 13.2    Ib = 1.9    T = 28.5

RX (до самопроверки)   43 00 82 00 17 1c 64 5c   Iw=13.0  Ib=2.3  T=28.0
RX (самопроверка #1)   43 00 83 00 16 9c 64 dc   Iw=13.1  Ib=2.2  T=28.5
RX (самопроверка #2)   43 00 84 00 15 9c 64 dc   Iw=13.2  Ib=2.1  T=28.5   ← точное совпадение по Iw и T
RX (самопроверка #3)   43 00 81 00 14 9c 64 d8   Iw=12.9  Ib=2.0  T=28.5
```

Раскладка: `b1–2 = Iw` (int16 BE, /10, нА), `b3–4 = Ib` (int16 BE, /10, нА), `b5 = T` (бит 7 → `(b−128)+0.5`), `b6` = байт из вендорской проверки питания, `b7` = сумма. `Iw` и `Ib` совпадают до десятых с показаниями на экране (небольшой разброс между тремя кадрами — секунды между самими самопроверками, живой электрохимический ток). Плавный рост температуры `28.0 → 28.5 °C` за ~15 минут физически согласован с прогревом сенсора.

**Это независимое живое подтверждение порядка `Iw` перед `Ib`** для CT2, отдельное от декомпилированного `ProtocolTools.Glucose` конструктора — тот же порядок и тот же масштаб `/10`, но в другой команде (`check`, а не push-запись глюкозы).

Init (`53 55 AA 52`) впервые прошёл в 20:58 — это и был момент запуска нового сенсора в Blueberry (см. B0). Через минуту пришла первая спонтанная нотификация 15 байт — **первая push-запись глюкозы**, id 0:

```

```

Побайтовый разбор по таблице выше:

| Байты | Поле | Значение | Проверка |
|---|---|---|---|
| 0 | opcode/маркер push | `0x44` | новое — вендорский конструктор `ProtocolTools.Glucose(byte[])` этот байт не проверяет, просто пропускает; в командах check/init/handshake/setDate `0x44` не встречается |

Через ~45 минут после старта сессии пришла живая пуш-запись `id=15`, а следом устройство само забэкфиллило пропуск `id=1…14` — по одной записи через `0x55 idHi idLo sum`, строго последовательно, ответ почти мгновенно после каждого запроса. Дальше цикл повторился ещё дважды (`id=16…18`, затем `id=19…24`) при каждом следующем реконнекте. Это ровно тот механизм, что описан в B3: «Бэкфилл по одной записи через `0x55` — серийного `0x22` у CT2 нет».

| id | opcode | время | Iw | Ib | T | заряд |
|---|---|---|---|---|---|---|
| 1–14 | `0x47` | 21:03…21:42, шаг ровно 3 мин | 12.4–14.2 | 2.1–2.4 | 29.0–30.5 | `0xFF` (255) |

**Найдено: у записи глюкозы два разных опкода, не один, как в §B1 выше предполагалось изначально:**

* **`0x44` — живой push** (спонтанная нотификация). Байт 13 несёт настоящий заряд трансмиттера — видно живое падение `100 → 96` за ~30 минут между записями `id=18` и `id=24`.

Остальные 14 байт (id, дата, `Iw`, `Ib`, температура, сумма) устроены идентично для обоих опкодов.

Шаг `id` — ровно 3 минуты на 24 подряд идущих записях (от `id=1` до `id=23`, с единственным естественным джиттером ±1–2 мин у живых push-записей относительно расчётного момента) — точное совпадение с `readingIntervalMinutes = 3` из профиля `SN08`. `Iw`/`Ib`/`T` образуют гладкую физиологическую кривую без аномалий, что дополнительно подтверждает корректность разбора (перепутанные поля дали бы рваный, не физиологичный ряд).

**Обновление для B1-таблицы:** строку «Запрос записи по id» и «формат push-записи» нужно читать как единый 15-байтный формат с двумя опкодами (`0x44` живой / `0x47` исторический), а не один опкод на оба случая.

### Попытка калибровки, 2026-09-07 22:22 MSK — калибровка не идёт через BLE

Через ~1.5 часа после старта (сенсор далеко не достиг суток) пользователь выполнил калибровку через интерфейс Blueberry. **В эфир не ушло ничего** — ни `08 mgdlHi mgdlLo sum` (референс к трансмиттеру), ни любой другой новый опкод; в логе за это время только очередной цикл handshake→setDate и одна push-запись (`id=28`).

Раньше в этом документе гейт «сенсор младше 24 часов» (`calibrationsUnavailableAnytimeSensorMinAge`, `pp+0x12d38`) был по ошибке распространён и на CT-14/Poctech. **Это неверно** — имя ключа в самом пуле строк буквально содержит `Anytime`, и это единственная строка такого рода во всём пуле: `PoctechSensorMinAge`, `SunlantSensorMinAge` или любого generic-варианта не существует. Гейт подтверждён только для семейства Anytime/CT3 (фаза A), для CT2 — нет оснований считать его действующим.

Отсутствие `0x08` при подтверждённой калибровке говорит в пользу другого объяснения: **калибровка Poctech в Blueberry, вероятно, полностью локальная** — пересчёт `slope`/`intercept` на стороне приложения по введённому референсу и текущим `Iw`/`Ib`/`T`, без обращения к трансмиттеру. Это соответствует модели affine-слоя из фазы A (§A1): `slope`/`intercept` пишутся в каждую запись при сохранении, а `0x08` — отдельная команда, которая двигает *внутреннюю* калибровку самого трансмиттера (его собственный K/R для `checkResponse`/`Glu` расчёта на борту) и не обязана вызываться из UI-потока «Calibrate».

**Закрыто статически, а не только по отсутствию трафика.** Проверил исходники `POCTech_xDrip_v_0.2.apk` (`jadx`, тот же источник, что и для B1): `inputBGMG_request`/`inputBGMG_response` определены только в `ist/com/sdk/ProtocolTools.java` / `ProtocolToolsHolder.java` — и **ни разу не вызываются** ни в `com.poctechcorp.pocct.*` (экраны), ни в `com.kamin.cgmblelib.*` (BLE-сервис). Команда `0x08` в этом приложении — неиспользуемая часть SDK.

Схема локальной Room-таблицы `glucose` подтверждает калибровку как полностью локальную: `Iw, Ib, T, bg, bgMG, Iw2…Iw7, Ib2…Ib4, Ib_avg, T_LastRef, LastKBeforeNewBG, K, k1, k2, k3, glu_mm, glu_mg, glucoseEstimate, mCalibrationStatus` — набор полей именно под локальный пересчёт (сглаженные окна тока, явные коэффициенты `K`/`k1`/`k2`/`k3`, «K до последней калибровки»), полностью в SQLite на телефоне, без обращения к трансмиттеру.

**Вывод для фазы A и B4:** модель Poctech ближе к affine-слою Blueberry (`slope`/`intercept` в каждой записи, §A1), чем к вендорской схеме `K0`/`inputKAndR`, привязанной к трансмиттеру. Для CT2 в JugglucoNG команду `0x08` реализовать в B1 всё равно стоит (это часть протокола, может пригодиться для совместимости или диагностики), но **основной путь калибровки должен быть локальным пересчётом, а не round-trip к сенсору** — ровно то, что уже спроектировано в A1.

**Запись глюкозы, 15 байт** (14 полезных + сумма; в одном пакете может быть несколько подряд):

| Смещение | Поле |
|---|---|
| 0 | опкод: `0x44` живой push, `0x47` ответ на pull (подтверждено вживую — см. ниже) |
| 1–2 | `id`, int16 big-endian |
| 3 | год = b + 2000 |
| 4–7 | месяц, день, час, минута |
| 8–9 | **`Iw`** = int16 / 10 (нА) |
| 10–11 | **`Ib`** = int16 / 10 (нА) |
| 12 | температура: бит 7 → `(b − 128) + 0.5`, иначе `b` |
| 13 | заряд трансмиттера на живом push; `0xFF` (не заряд, сентинел) на ответе pull |
| 14 | сумма |

> В CT2 порядок `Iw, Ib`; в CT3 и CT2.5 наоборот, и масштаб другой (целое плюс дробная часть /100 вместо /10). Перепутанные `Ib` и `Iw` дадут правдоподобные, но систематически неверные значения — на глаз не ловится, только тестом на зафиксированном кадре.

**Приёмка.** Побайтовое сравнение каждого билдера с эталоном; round-trip парсера на реальном кадре из B0; отдельная проверка порядка `Iw` / `Ib`.
